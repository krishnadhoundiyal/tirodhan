# Schema Design

## Purpose

This document defines the approved PostgreSQL/PostGIS physical-schema conventions and table-level shape before implementation.

Coding agents must treat these as architecture constraints rather than suggestions.

## Global conventions

```text
Database              PostgreSQL + PostGIS
Naming                snake_case
Primary keys           UUID
UUID generation        UUIDv7 generated by application
Timestamps             timestamptz, UTC
Money                  bigint minor units
Spatial location       geography(Point, 4326)
Lifecycle              explicit status columns
History                append-only where history matters
Deletes                deliberate; no universal soft-delete flag
Concurrency            DB constraints + transactions + selective versioning
Idempotency            DB-enforced and domain-enforced
```

### IDs

Use UUID primary keys for business entities. Prefer application-generated UUIDv7.

### Money

Store money as integer minor units, e.g. `₹249.50 -> 24950`. Never use floating point for money.

### Time

Use `timestamptz` for real instants. Pickup slots are represented as actual `slot_start` and `slot_end` instants.

### Spatial data

Canonical location is `geography(Point, 4326)`. Use PostGIS indexes/predicates rather than custom latitude/longitude arithmetic.

### Status values

Prefer `varchar` plus application enums and appropriate DB checks rather than proliferating PostgreSQL ENUM types during early product evolution.

### Deletion

Do not add `is_deleted` everywhere. Use domain semantics such as `ARCHIVED`, `DISABLED`, or `INACTIVE`; retain financial/operational history.

### Foreign keys

Use real foreign keys. ORM relationships are not a substitute for referential integrity. Avoid cascading deletion of historical business records.

### JSONB

Use JSONB only for genuinely variable non-core metadata. Do not use it as a substitute for relational modelling of addresses, payments, collection items, assignments, or lifecycle history.

### `refresh_session`

**Implementation status: intentionally provisional.**

The authentication architecture requires a revocable refresh-session mechanism and forbids plaintext refresh credentials, but the exact retry/rotation/replay semantics are still open. Therefore this table must not be implemented from a rotating-token draft until ADR-007 is resolved.

Schema invariants that are already approved:

```text
- durable session identity related to app_user;
- explicit expiry and revocation state/timestamps;
- no plaintext refresh credential storage;
- cryptographic verifier/hash material appropriate to the chosen mechanism;
- database protection for the chosen replay/concurrency semantics.
```

Fields such as `token_family_id`, `ROTATED` status, rotation links, grace/retry markers, or an alternative stable-session representation are strategy-dependent and are not yet approved physical schema.

Before implementing authentication migrations, resolve the lost-success-response case described in ADR-007 and update this section with the final table shape and constraints.

## Important transactional boundaries

### Payment acceptance

One transaction persists:

- successful payment attempt;
- logical payment success;
- request `PENDING_PAYMENT -> ACCEPTED`;
- acceptance timestamp;
- outbox event.

### Cancellation and refund creation

One transaction persists:

- request `ACCEPTED -> CANCELLED`;
- refund record;
- refund-requested outbox event.

### Planning freeze

One transaction creates/finds the unique planning batch and moves eligible `ACCEPTED` requests to `PRE_PLANNING` with immutable `planning_batch_id`.

### Planning completion

One transaction persists:

- collection groups;
- group membership;
- pickup executions;
- requests `PRE_PLANNING -> PLANNED`;
- batch `-> COMPLETED`;
- outbox events.

### Assignment acceptance

One transaction ensures the group is still assignable, the rider is still eligible/idle, one assignment wins, the rider work state changes consistently, and the offer is updated.

### Reassignment

One transaction closes/partially completes the predecessor assignment, releases only outstanding items, creates the successor assignment, attaches outstanding pickup executions, reserves the replacement rider, and writes the outbox notification.

### Handover completion

One transaction validates the receiving point/evidence and collected pickups, marks the handover/items validated, moves associated collection requests to `COMPLETED`, and writes completion outbox events.
